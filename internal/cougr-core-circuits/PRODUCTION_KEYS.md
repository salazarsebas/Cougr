# Production Verification Keys: `with_verification_key` Guide

## Scope

This document covers taking the output of a completed [ceremony](./CEREMONY.md) — a `<circuit>_vk.json` file — and
getting it into a deployed Cougr contract via `GameCircuitSpec::with_verification_key`. It assumes you already have
a production `<circuit>_vk.json` from a real multi-party ceremony, not the single-contributor output of
`scripts/setup.sh`.

## Why this is a separate step from the pipeline

Every builder in `cougr_core::circuits` (`fair_dice`, `hidden_cards`, `fog_of_war`, `sealed_bid`) returns a
`GameCircuitSpec` with the **pipeline test verification key** already embedded — the one generated by
`scripts/setup.sh` and baked into `src/circuits/generated.rs` by `export-soroban-artifacts.mjs`. That key is
committed to this repo, has a single known contributor, and is explicitly documented as development-only
(`generated.rs` is headed "Development-only — never ship CI-generated VKs to production mainnet").

`with_verification_key` exists specifically to swap that test key out:

```rust
// src/circuits/spec.rs
pub fn with_verification_key(mut self, vk: VerificationKey) -> Self {
    self.verification_key = vk;
    self
}
```

Every production deployment of a Cougr ZK circuit must call this before the spec is used to verify any real proof.

## Step 1: Get your VK bytes into Rust

`VerificationKey` (`cougr_core::zk::VerificationKey`) is a `Vec<G1Point>` / `G2Point` struct, not something you
construct from JSON directly. The supported path is `VerificationKey::from_raw_bytes`:

```rust
use cougr_core::zk::VerificationKey;

let vk = VerificationKey::from_raw_bytes(
    &env,
    &VK_ALPHA,  // [u8; 64]  — G1
    &VK_BETA,   // [u8; 128] — G2
    &VK_GAMMA,  // [u8; 128] — G2
    &VK_DELTA,  // [u8; 128] — G2
    &VK_IC,     // &[[u8; 64]] — one G1 chunk per public input, plus 1
);
```

Byte counts must match `PublicInputLayout::public_input_count() + 1` for `ic.len()`, or `verify()` returns
`ZKError::InvalidVerificationKey`.

## Step 2: Converting `<circuit>_vk.json` to those byte arrays

This is the part worth slowing down for, because **there are two documented byte-layout conventions for G2 points
in this codebase, and they disagree**:

- `src/zk/interop.rs` (the `from_raw_bytes` doc comment) describes the layout as `x_c0 ‖ x_c1 ‖ y_c0 ‖ y_c1`, and
  says it matches what `snarkjs zkey export rawcalldata` produces.
- `internal/cougr-core-circuits/scripts/export-soroban-artifacts.mjs` — the script this repo's own pipeline uses
  to go from `vk.json` straight to embedded Rust constants — encodes G2 as `x_c1 ‖ x_c0 ‖ y_c1 ‖ y_c0` (it reads
  the raw `vk_beta_2` / `vk_gamma_2` / `vk_delta_2` arrays from snarkjs's JSON directly, not through
  `rawcalldata`), with an explicit comment: *"snarkjs stores Fq2 as `[c0, c1]`; Soroban expects `c1 || c0` per
  coordinate."*

These are two different source formats (`vk.json`'s native array layout vs. `rawcalldata`'s hex output), so they
aren't necessarily contradictory — but if you build your own conversion script instead of reusing this repo's, it
is easy to pick the wrong ordering for whichever source you're reading from, and a wrong ordering can produce a VK
that either fails every proof or, worse, fails silently in a way that isn't caught until mainnet. **Treat this as
a real risk, not a formality**, and verify against a known-good VK before trusting a new conversion path (see
"Verify before you ship" below).

**Recommended path — reuse the working script, don't hand-roll a converter:**

1. Put your ceremony's `<circuit>_vk.json` (and a corresponding real `proof.json` / `public.json` for a test
   witness) where `internal/cougr-core-circuits/scripts/export-soroban-artifacts.mjs` expects them (`exported/`
   and `work/<circuit>/` respectively).
2. Run it in a scratch branch, **not against your real `src/circuits/generated.rs`**:
   ```bash
   cd internal/cougr-core-circuits
   bun scripts/export-soroban-artifacts.mjs
   ```
   This emits the same `[u8; 64]` / `[u8; 128]` Rust constant arrays the pipeline uses for test keys, but now
   sourced from your production VK. Copy the constants for your circuit out of the generated file — do **not**
   let this overwrite the committed `generated.rs`, which must stay the test pipeline's output.
3. Wire those constants into your own application code (not this repo) via `VerificationKey::from_raw_bytes`, as
   in Step 1.

If you'd rather convert by hand or in your own tooling, match `export-soroban-artifacts.mjs`'s convention
(`fpToBe32`, big-endian, G1 as `x‖y`, G2 as `x_c1‖x_c0‖y_c1‖y_c0`) since that's the convention this repo's own
passing on-chain tests are built against — then verify, don't assume.

## Step 3: Apply it to the circuit spec

```rust
use cougr_core::circuits::fair_dice;

let spec = fair_dice(&env, sides, &seed_commitment)?
    .with_verification_key(vk);
```

Do this at the point your contract constructs the spec for a real game — not just once in a test — since
`with_verification_key` returns a new `GameCircuitSpec` rather than mutating a stored one in place.

## Step 4: Verify before you ship

Before deploying:

- Run `scripts/verify-rejects-invalid.sh <circuit>` (or equivalent) against your production VK with a known-good
  proof and a deliberately-broken one, and confirm the good proof passes and the bad one fails.
- Run Cougr's own integration tests with your production VK substituted for the pipeline VK, per the "Re-run
  Cougr integration tests after VK swap" note in [AUDIT.md](./AUDIT.md).
- Confirm `ic.len()` equals your circuit's public-input count plus 1 — a mismatch is caught at verify-time
  (`ZKError::InvalidVerificationKey`), but confirming it ahead of a mainnet deploy is cheaper than debugging it
  live.
- Double check you're embedding the **verification** key, not the proving key. The ceremony produces both; only
  the verification key belongs in a contract or client-visible constant.

## Common mistakes this guide exists to prevent

- Shipping the committed `src/circuits/generated.rs` constants (pipeline test keys) to mainnet — check your
  contract isn't importing `cougr_core::circuits::embedded::pipeline_verification_key` or the test builders'
  default VK for a production deployment; always call `with_verification_key` explicitly.
- Mixing G2 byte-order conventions between a `vk.json`-based converter and a `rawcalldata`-based one within the
  same key.
- Reusing one circuit's production VK for a variant with a different public-input layout (different deck size,
  different board size, etc.) — each variant needs its own ceremony and its own `CircuitId` per
  [AUDIT.md](./AUDIT.md)'s public-input freeze policy.
