# Current State Assessment

*Part 2 of 17. Findings from a direct audit of the repository at commit range through `9e4088e` (2026-07-23) and the public crates.io / docs.rs / GitHub surfaces.*

## Architecture and technical foundation

Cougr ships as a single publishable crate, `cougr-core` (v1.1.0, MIT, `no_std`, targeting `wasm32v1-none`), with three internal, unpublished workspace subcrates (`internal/cougr-core-circuits`, `internal/cougr-core-session`, `internal/cougr-core-test`) that exist only so the corresponding modules can be `cargo check`ed in isolation, then `include!`d back into the main crate. This is a deliberate, documented workaround (ADR 0007) to keep crates.io metrics unified under one package while still getting compile isolation. It is a reasonable choice for now and should not be read as "the project doesn't understand workspaces."

The public API is organized into curated namespaces rather than a flat module list: `app` (default runtime, `GameApp`), `auth` (account abstraction, Beta), `privacy` (ZK, split stable/experimental), `ops` (OpenZeppelin-style standards, Stable), `prelude`, and `runtime` (advanced composition). Two interchangeable ECS backends exist, `SimpleWorld` (map-based, recommended default) and `ArchetypeWorld` (signature-grouped, for larger entity counts). Three component macros cover fixed-size primitives, observed primitives (which emit indexer-friendly Soroban events), and rich XDR-codec components for `Address`/`Vec`/`String`/nested structs.

The differentiated technical surface, relative to any other ECS or game framework studied, is entirely in three places: account abstraction with session keys and secp256r1 (WebAuthn/passkey) support (`src/accounts/`), four ZK "game circuit" builders for hidden information and fairness (hidden cards, fog of war, fair dice, sealed bid, using Groth16/BLS12-381/Poseidon2 via Stellar's Protocol 25 host functions), and the standards layer (`Ownable`, `AccessControl`, `Pausable`, execution guards). No general-purpose ECS, and no other on-chain gaming framework surveyed in this research, bundles all three of these in one crate. This is the actual moat. It should be the headline of every piece of marketing copy the project produces, not the ECS itself (ECS is table stakes, ZK-backed hidden information and passkey account abstraction on a smart-contract chain are not).

## Developer experience today

There is no CLI. No `cougr new`, no `cargo generate` template, no scaffolding binary. All build and deploy tooling is the stock `stellar` CLI (`stellar contract build`, `stellar contract deploy`). The closest thing to project scaffolding is `skills/cougr-game-starter/SKILL.md`, an AI-agent prompt playbook meant to be run by Claude Code, not a piece of software a developer installs and runs themselves. This means a developer without an AI coding assistant, or one who prefers a deterministic tool over a prompt, has no first-class path from "I have an idea" to a running project. They must find an example that resembles what they want, copy it, and manually rename things.

This is the single largest gap between Cougr's technical maturity and its developer experience maturity, and it is discussed at length in [08-ux-strategy.md](./08-ux-strategy.md) and prioritized in [14-prioritized-opportunities.md](./14-prioritized-opportunities.md).

## Documentation: a genuine strength, poorly surfaced

Documentation is disproportionately mature for a repository whose first commit was 2025-10-13. There are 20 top-level docs plus 5 ADRs: an architecture doc, a changelog with honest stability notes, a contributing guide with a "Public API Checklist," a security policy that explicitly disclaims external audit, and a set of self-auditing documents (`STATE_OF_REPO.md`, `RELEASE_STATUS.md`, `PUBLIC_GAPS.md`) that state the project's own gaps in plain language rather than hiding them. The `MATURITY_MODEL.md` (Stable / Beta / Experimental) is applied consistently across the README, changelog, and security policy, which is a discipline most projects claim and few actually maintain.

The problem is not quality, it is packaging. There is no documentation site: no mdBook, Docusaurus, or MkDocs configuration anywhere in the repo. `docs/DOCUMENTATION.md` explicitly withholds adding a docs.rs badge "until that URL has been opened and verified," yet this research verified that docs.rs is live and rendering well (48% doc coverage, clean module structure, a "Golden Path" example baked into the crate doc). That gap between "the docs are actually good" and "the project's own docs say we haven't checked" is itself a symptom: the team is heads-down on the crate and examples, and the outward-facing presentation has fallen behind the internal reality. Fixing this is closer to a documentation site build than a rewrite; the content largely exists already. See [12-documentation-architecture.md](./12-documentation-architecture.md).

## Examples: a large, underused asset

39 example games exist, 10 held to a formal "canonical" standard (`EXAMPLE_STANDARD.md`: consistent `lib.rs`/`components.rs`/`systems.rs` layout, README structure, dependency hygiene) and 29 "transitional" examples that are being actively migrated forward, visible in the current PR activity (#226, #228, #233, #236, #237). This is a genuinely large content library, spanning arcade games (Snake, Pong, Asteroids, Space Invaders), board games (Chess, Checkers, Reversi, Connect Four), puzzle games (Sudoku, Minesweeper, Memory Match), card and hidden-information games (Battleship, Blind Auction, Hidden Hand), and one example (`murdoku`) with a full React 19 + Vite + Tailwind frontend, the only example demonstrating an actual player-facing client.

Right now this library only exists as a source tree a developer has to clone and read to discover. There is no gallery, no screenshots, no "try it" link, no categorization surfaced anywhere public. This is the second largest gap after the missing CLI: real content sitting invisible.

## Branding, community scaffolding, and governance

Branding is close to nonexistent beyond a single 1024x1024 logo PNG and four shields.io badges. There is no website, no color palette, no typography system, no design tokens. Community scaffolding is partial: `CONTRIBUTING.md` and `SECURITY.md` are unusually rigorous, but there is no `CODE_OF_CONDUCT.md`, no GitHub issue or PR templates, and no `GOVERNANCE.md`, despite 25+ distinct external contributors having landed commits. This is a real risk today, not a someday problem: active contributors are currently operating without a documented code of conduct or a documented decision-making process.

## The traction signal: 8 stars, 51 forks

This ratio is the clearest single data point in this audit. Forks that outnumber stars by 6x almost never happen organically; it is the signature of a structured contribution program (bounties, hackathon tasks, an OnlyDust-style board) where people fork to complete a task, not because they discovered the project and want to follow it. The git log confirms this: 25+ distinct contributors, bursty commit velocity aligned to specific issue numbers, and merge-conflict-resolution commits from multiple concurrent PRs landing against the same shared files. The engineering culture is real and active. The public discovery funnel (would a developer searching "on-chain game engine Stellar" find this, understand it in 30 seconds, and want to try it) is not yet built. This assessment should be read as the throughline for the rest of this package: build the parts of the funnel that convert quality into visible traction before building anything speculative.

## Technical debt, in the project's own words

The project already tracks its own gaps honestly, which is a strength worth preserving as a norm. Notable flagged items: the ZK circuits ship test-tier trusted-setup keys only, with an explicit warning against production use pending an independent ceremony (`internal/cougr-core-circuits/AUDIT.md`); 7 canonical examples depend on `cougr-core` via a local path rather than the published crate, pending a version catch-up; the crate exposes more public surface than its stability guarantees cover; and `auth`/`accounts` remains intentionally Beta despite being functionally complete, because account abstraction is judged too security-sensitive to freeze early (ADR 0002). None of this is hidden. The recommendation throughout this package is to keep this radical-honesty documentation culture as a core brand asset (see [09-design-strategy.md](./09-design-strategy.md)), not to paper over it in service of looking more finished than the project is.
