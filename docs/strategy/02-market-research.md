# Market Research: What Great Developer Platforms Have in Common

*Part 3 of 17. Patterns extracted from game engines, on-chain game frameworks, and general developer platforms, with a focus on principles Cougr can apply rather than surface-level imitation.*

## Game engines: the onboarding-to-output loop

Unity, Godot, and Bevy solve the same problem three different ways, and the differences are instructive.

**Unity and Godot** front-load a visual editor. The very first thing a new user sees is a scene with an object in it they can move. The gap between "opened the tool" and "something exists on screen" is seconds. This is the single biggest lever either platform pulls, and it is largely inapplicable to Cougr directly (there is no visual scene for on-chain state), but the underlying principle transfers: minimize time-to-first-visible-result. For Cougr that result is not a rendered sprite, it is a passing test against a running contract, or a deployed testnet game with a URL you can share. The CLI strategy in this package is built around compressing that gap to under two minutes.

**Bevy** is the closest engine analog to Cougr's actual architecture: a Rust-native ECS with a plugin system, no visual editor, and a documentation-and-examples-driven onboarding path instead. Bevy's `examples/` directory, indexed with screenshots and one-line descriptions on its website, is effectively the model for what Cougr's 39 examples should become (see [08-ux-strategy.md](./08-ux-strategy.md)). Bevy also demonstrates the risk of Cougr's current path if left unaddressed: a technically excellent ECS with a famously steep initial learning curve, mitigated over years by community-maintained cheat sheets and third-party "quick start" content the core team didn't originally build. Cougr has the chance to build that quick-start layer from day one instead of waiting for the community to compensate for its absence.

**Scratch, GDevelop, and Construct** matter here not as architectural models but as a reminder that "on-chain game development" will eventually need a no-code or low-code on-ramp if the ecosystem wants to reach game designers and educators, not just Rust engineers. This is explicitly out of scope for near-term Cougr (see [05-ecosystem-vision.md](./05-ecosystem-vision.md) for why a visual editor is sequenced late), but the documentation and example structure should be written so that a technical artist or designer, not just a systems programmer, can follow along without needing to understand Rust ownership semantics to read the first tutorial.

## On-chain game frameworks: the direct comparables

**Dojo** (Starknet) and **MUD** (Ethereum/OP Stack, by Lattice) are the closest existing products to what Cougr is building, an ECS pattern for fully on-chain state. Both made the same early bet Cougr is making now: ECS as the natural fit for on-chain game state because component data maps cleanly onto contract storage. Both also invested heavily, and early, in a CLI (`sozo` for Dojo, MUD's own CLI) as the primary onboarding surface, ahead of documentation polish or visual tooling. That sequencing choice, CLI before almost everything else, is the strongest evidence in this research that Cougr's current CLI gap is the correct first priority, not a nice-to-have.

**Cartridge** (built on Dojo) is worth studying specifically for its account abstraction and "session-based" player onboarding, letting players interact with on-chain games without a wallet popup on every transaction. Cougr's `SessionManager` and `SessionBuilder` already solve a version of this problem at the contract level; the gap is that Dojo/Cartridge pair their contract-level session support with a polished client SDK and wallet integration story, while Cougr's session and account-abstraction work currently has no equivalent client-side story beyond the single `murdoku` example. This is a concrete, scoped opportunity: a thin, well-documented client SDK (TypeScript) that talks to `cougr-core` session and account primitives the way Cartridge's controller talks to Dojo, would close a real gap. See [06-product-strategy.md](./06-product-strategy.md).

**Lattice's** broader thesis, that "autonomous worlds" need infrastructure beyond just the contract layer (indexing, client sync, tooling), is a useful cautionary signal on scope: Lattice built MUD, then a hosted indexer, then a client sync layer, over multiple years and with venture funding. Cougr should study the sequencing (contract layer first, infra second, always in response to real usage) without assuming it needs to replicate the full stack immediately or with the same funding profile. See [07-business-strategy.md](./07-business-strategy.md) on sustainable pacing.

## Developer platforms: the productization patterns worth borrowing

**Supabase and Vercel** are the strongest analogy for what Cougr should aspire to as an experience, not as a literal architecture. Both pair an open-source core (which can be run and understood independently) with a CLI that scaffolds a working project in one command, and a hosted layer that is entirely optional. Nobody is forced to use Supabase Cloud to get value from Supabase; the CLI and local dev experience stand alone. This is the exact composability principle already stated as a north star for Cougr, and it argues for a CLI that works fully offline against local test ledgers before any hosted service exists.

**shadcn/ui** demonstrates a distribution model worth adopting almost directly: instead of an installed dependency, components are copied into your project as source you own and can modify, with a CLI (`npx shadcn add button`) that fetches them. Cougr's account, standards, and circuit modules could offer an equivalent for scaffolding, `cougr add session-arena` or `cougr add hidden-hand` pulling a working component/system pair from the example library directly into a new project, rather than requiring a developer to hand-copy files from `examples/`. This maps directly onto the existing example library and requires no new content, only a distribution mechanism (see [11-skills-strategy.md](./11-skills-strategy.md) and [06-product-strategy.md](./06-product-strategy.md)).

**GitHub, Linear, and Figma** share a design discipline more than a technical pattern: restrained visual language, generous whitespace, purposeful motion, and consistent terminology used identically across marketing site, product UI, and documentation. The lesson for Cougr is narrower than "make it pretty," it is "pick a small vocabulary and never deviate." Cougr already has the beginnings of this in its Stable/Beta/Experimental maturity model; the design system work (see [09-design-strategy.md](./09-design-strategy.md)) should extend that same discipline into visual design rather than introducing a second, unrelated vocabulary.

**Turborepo** is relevant to the repository strategy question directly: it demonstrates that a single, well-organized monorepo with clear package boundaries can support a large ecosystem (many packages, one source of truth, one CI, one versioning story) without needing to fragment into many repositories prematurely. See [10-repository-strategy.md](./10-repository-strategy.md) for the recommendation this leads to.

## Cross-cutting pattern summary

Across every product studied, four things recur regardless of category: a scriptable CLI or generator as the true front door (not the docs, not the website); documentation and examples treated as one interconnected system rather than separate deliverables; a small and consistently applied vocabulary (naming, stability tiers, visual language) used identically everywhere; and a hosted or premium layer that is additive, never required to get real value. Cougr already has the raw material for all four. None of the four require inventing new technology, they require packaging and sequencing decisions, which is what the rest of this package specifies.
